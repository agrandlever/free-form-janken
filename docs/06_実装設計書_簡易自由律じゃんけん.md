# 実装設計書：簡易自由律じゃんけん

## 1. 基本方針

アプリケーション内部では、現在の状態とスナップショットを分離する。

```text
GameUser
  │
  ├─ OriginalHand
  │
  └─ Room
       │
       └─ GameMatch
            ├─ MatchParticipant
            ├─ OriginalHandSnapshot
            ├─ Round
            ├─ RoundResult
            └─ MatchResultSnapshot
```

現在のユーザー・ルーム・オリジナル手は更新可能。

対戦開始時のルール・参加者・オリジナル手、確定済みラウンド、終了済み対戦はスナップショットとして保持し、後から現在データを変更しても書き換えない。

### 1.1 採用技術とプロジェクト基盤

- Java 21 / Spring Boot 4.1.1。
- Gradleを使用し、Gradle Wrapperでビルド・起動・テストを実行する。
- Spring Web、Thymeleaf、Validation、Spring Boot Testを採用する。
- DBは使用せず、JPA、H2等のDB関連依存関係を追加しない。
- プロジェクト基盤の作成範囲は30節の第0段階に従う。

### 1.2 文字列の共通判定基準

ユーザー名・ルーム名・オリジナル手名の前後空白除去、保存、重複判定、文字数判定には、次の共通基準を適用する。

- サーバーでJava `String.strip()`の規則により前後空白を除去する。本書の「前後空白」「空白だけ」の判定も、この規則を基準とする。
- 保存・表示する値と重複判定に使用する値は、除去後の値とする。
- 文字数は除去後のUnicodeコードポイント数（Unicodeの文字を表す符号位置の個数）で数える。Java `String.length()`ではなく、`value.codePointCount(0, value.length())`を使用する。
- 「1～20文字」は、除去後のUnicodeコードポイント数が1～20であることを意味する。未入力または除去後に空になる入力は拒否する。
- JavaScript側のチェックは補助とし、最終判定はサーバーを正とする。

AuthService、RoomService、OriginalHandServiceと各Formは同じ整形・文字数判定基準を用いる。String.trim()やString.length()だけによる文字数検証へ置き換えない。除去後のusername・roomName・nameをDomainとStoreへ保存する。入力不正時の再表示用formは、既存の入力値保持仕様に従って別に扱う。

### 1.3 時間取得と期限の共通基準

5秒・10秒・30秒はサーバー上の期限として扱い、実時間での画面切替との完全一致を要求しない。

- ラウンド結果の期限は結果確定時刻＋5秒または＋10秒、通信切断の期限は最後の正常状態確認時刻＋30秒とする。入室直後は入室時刻を通信監視の基準とする。
- 期限より前に、時間経過を理由とする状態遷移・切断処理を行ってはならない。
- MatchTransitionScheduler（対戦の自動遷移を確認する定期処理）は500ms間隔、DisconnectMonitor（切断を確認する定期処理）は1秒間隔で確認し、期限到達後の次回実行時に、共通ロック内で最新の状態と時刻を確認して更新する。
- ブラウザーの状態確認は2秒間隔とし、サーバー状態変更後の次回状態確認で表示へ反映されればよい。カウントが0になったことだけで画面側が状態を確定しない。
- 時間依存ロジックはJava `Clock`等（現在時刻を取得する仕組み）を利用し、テストで現在時刻を制御可能にする。期限前の非遷移と期限到達後のScheduler実行による遷移を分けて検証し、実時間の完全一致を合否条件にしない。

人数不足による即時中止や手動退出等、時間経過によらない既存の処理はこの待機期限の対象ではなく、従来どおり実行する。最終勝者確定後は、期限到達後の正常終了処理が完了するまで正常結果の保護と残存参加者の④を維持する。

Service・Schedulerにはテストで差し替え可能なClock等を渡し、ログイン・入室・lastSeenAt・joinedRoomAt・startedAt・decidedAt・transitionAt・finishedAt・statusのserverTimeを同じ時刻取得基準で扱う。現在時刻を取得する処理を各所に固定して、テストから制御不能にしない。必要な時刻は共通ロック内で取得し、判定結果と表示用コピーの整合を保つ。

## 5. GameUser

役割：現在ログイン中のユーザー状態を管理する。

```text
UUID id
String username
UserState state
UUID currentRoomId
OriginalHand originalHand
Instant joinedRoomAt
Instant lastSeenAt
```

ログイン時はstate=ROOM_NONE、currentRoomId=null、originalHand=null、lastSeenAt=ログイン時刻。正常入室時にjoinedRoomAt・lastSeenAtを入室時刻へ設定する。

結果の閲覧対象はユーザーやセッションの単一フィールドに保存しない。各タブの結果URL・HTML制御用matchId・フォームのresultMatchIdが対象を保持する。

「ルームへ戻る」や観戦操作はそのタブのページ移動だけを行う。他タブの対象を解除・変更しない。

ユーザー状態と結果の対象を分離する。次対戦開始で③→④になった本人は全タブで現在対戦を優先し、退出・切断・ログアウト・別ルーム所属ではアクセス制御を優先する。

## 15. MatchResultSnapshot

終了済み対戦を、現在のGameMatch・GameUserを参照せず再現できる形で保持する。

```text
UUID matchId
UUID roomId
String roomName

int targetWins
boolean preventConsecutiveSameOriginalHand

Map<UUID, String> participantNames
MatchEndType endType
List<UUID> winnerIds
Map<UUID, Integer> finalScores

List<RoundResult> roundHistory
List<OriginalHandSnapshot> originalHandAffinities

Instant finishedAt
```

`participantNames` は開始時の全参加者の内部ユーザーIDと開始時点のユーザー名を保持する。

`finalScores` も開始時の全参加者を含め、途中退出者・0勝の参加者を除外しない。両Mapのキー集合は一致させる。

勝者名は `winnerIds` と `participantNames` から取得する。途中退出者の名前を現在のUserStoreから復元しない。

ルール、参加者名、最終勝数、確定済み履歴、全オリジナル手相性は終了時に保存用コピーを作成し、その後変更しない。

Map・Listだけでなくその要素も、後から変更できる元オブジェクトと共有しない。現在のオリジナル手更新とは独立させる。

## 16. 勝敗判定

### 通常手同士

通常のじゃんけん。

### オリジナル手対通常手

OriginalHandSnapshotの対応相性を使用する。

### 同一オリジナル手

同一 `handId` なら引き分け。

### 異なるオリジナル手

双方の `vsOriginal` を組み合わせる。

| A | B | 結果 |
|---|---|---|
| WIN | LOSE | A勝ち |
| LOSE | WIN | B勝ち |
| WIN | WIN | 引き分け |
| LOSE | LOSE | 引き分け |
| DRAW | WIN | B勝ち |
| DRAW | LOSE | A勝ち |
| WIN | DRAW | A勝ち |
| LOSE | DRAW | B勝ち |
| DRAW | DRAW | 引き分け |

## 17. RoundJudgeService

責務：ラウンド勝敗計算だけを担当する。参加者のscore・previousHand、対戦状態、Storeを変更しない。

主なメソッド：

```text
judgeRound(activeParticipants, selections, originalHands, decidedAt)
compareHands()
```

各active参加者について他の全active参加者と比較し、hasWin=trueかつhasLoss=falseなら、その参加者のwonRound=trueとする。1勝の加算はMatchService.completeRound()だけが行う。

返却するRoundResultはuserId・開始時のusername・手名・wonRoundを含む変更しないコピーとする。累積勝数と個別相性は含めない。

## 18. RoomService

主な責務：

```text
enterRoom()
leaveRoom()
updateRules()
ready()
cancelReady()
startMatch()
transferHost()
```

すべて29節のGameStateLockを使用する。純粋な入力整形以外の状態確認・更新・Store参照は同じロック内で行う。

### enterRoom

1. セッションのユーザーが①かつcurrentRoomId=nullであることを確認する。
2. roomNameを整形・検証する。
3. strip後の名前でルームを検索する。
4. 存在しなければRoomを新規作成する。初期ルールは先取3・連続禁止OFF。
5. 既存ルームは8人未満を確認する。満員ならROOM_FULLで拒否する。
6. memberIdsへ1回だけ追加し、currentRoomId・joinedRoomAt・lastSeenAtを設定して②にする。

上記全体を同じロック内で完了する。拒否要求で新規空ルーム・二重所属を残さない。既存ルームが対戦中でも現在対戦のparticipantsへ追加しない。

未ログインは共通アクセス制御で401 / LOGIN_REQUIRED。ログイン済みの②・③・④、または所属ありは、roomNameが不正でも1の確認で409 / INVALID_STATEとして拒否する。①・未所属の確認に成功した要求だけで、2の入力値不正を400 / VALIDATION_ERRORとする。API5.3節と同じ検証順序をController・Formからの呼び出しでも守る。

同名作成・同時8人上限・同一ユーザーの別ルーム入室・最後の退出による削除との競合を同じロックで防止する。

### leaveRoom

退出前のstate・roomId・現在対戦IDを先に保持する。

1. 対象roomIdと現在所属を確認。
2. memberIdsから除外し、GameUserを①・currentRoomId=nullとする。
3. 退出前に④だった場合、保存した対戦IDでMatchService.handleParticipantLeave()を呼ぶ。
4. ホストなら最古参の残存メンバーへ移譲する。
5. 0人ならRoomStoreとroomIdByNameから同じ内部IDのルームを削除する。

ログアウト・切断もこの退出手順を使用する。正常終了待ちの対戦はルーム削除後も保持する。

RoomService.leaveRoom()ではGameUserのid・username・originalHandとセッションのログイン状態を維持する。手動のPOST /room/leaveはこの処理後に302で /roomsへ戻す。POST /logoutの場合だけ、AuthServiceが退出処理後にセッションのログイン状態を終了する。

### ready / cancelReady

readyは②、cancelReadyは③のみ。要求roomIdと現在所属を検証する。

readyはオリジナル手存在確認→③一覧取得→ユーザー名・手名の両重複確認→③へ変更を同じロック内で行う。複数重複をまとめて返し、先行要求反映後の状態で後続要求を判定する。

cancelReadyは③→②。取消・保存・開始が途中へ割り込まないようにする。

### updateRules

要求roomIdと現在所属の一致を確認後、実行者が現在ルームのホストであることを先に検証する。その後、②または③・進行中対戦なし・入力値有効を検証する。

非ホストはFORBIDDEN、対戦中・状態不一致はINVALID_STATE、値不正はVALIDATION_ERROR。拒否時にルール・ユーザー状態を変更しない。正常更新でも③を解除しない。

### startMatch

対戦開始要求の入口とし、開始条件の検証・実際の開始処理への委譲を担当する。

GameStateLockを保持したまま、次の順で行う。

1. 要求roomIdが現在所属と一致することを確認。
2. 操作者がホストであることを確認。
3. 操作者が②または③で、進行中対戦がないことを確認。
4. 現在③の参加者を入室順で確定し、2人以上であることを確認。
5. オリジナル手存在、参加者間のユーザー名・手名非重複を最終確認。
6. 検証済みRoomと参加者一覧をMatchService.startMatch()へ渡す。

ここではGameMatch・スナップショットの生成や③→④は行わない。検証から委譲先の開始完了まで同じロックを保持する。条件不成立なら対戦・ルーム・ユーザー状態を変更しない。

## 19. OriginalHandService

主な責務：save()・delete()・validate()。

操作可能は①・②。returnPage・roomId・resultMatchIdの整合をAPI13・14節どおりに検証する。③・④、旧ルーム・他ルーム結果の返却先では保存・削除しない。

ほかの状態・返却先条件が有効な要求では、必須IDの未指定・空文字・UUID形式不正を400 / VALIDATION_ERROR、形式が正しいIDの所属・結果対象不一致を409 / INVALID_STATEとする。不存在・未終了・他ルームのresultMatchIdも後者とする。保存・削除の双方でAPI13・14節と同じ区別を用いる。

未作成なら新規作成、作成済みなら既存IDを維持して更新する。

作成・更新とも、nameの前後空白を1.2節のString.strip()で除去し、空でないこと・除去後1～20コードポイント・禁止名との非一致・相性4項目・最低1項目LOSEを検証する。Formの文字数判定と禁止名判定も除去後に適用する。

禁止名は「グー」「チョキ」「パー」の3つだけとし、除去後のnameとの完全一致で判定する。部分一致では拒否しない。FormとServiceで同じ禁止名集合・判定基準を使用し、APIへの直接要求もServiceで拒否する。LoginForm.usernameやRoomEnterForm.roomNameには、この禁止名判定を適用しない。

禁止名は400 / VALIDATION_ERRORとし、nameの項目エラーとerrorMessagesに `オリジナル手の名前に「グー」「チョキ」「パー」は使用できません。` を返す。検証成功前にOriginalHandを生成・更新・Storeへ反映しない。

検証成功後だけ更新し、不正な更新では既存の名前・相性・内部IDを変更しない。

save・deleteと準備・開始・退出を同じGameStateLockで保護する。結果画面の更新・削除をMatchResultSnapshotへ反映しない。

返却先は検証済みreturnPageと、フォームが保持するresultMatchIdから組み立てる。他タブやlastCompletedMatchIdで返却先を変更しない。

## 20. MatchService

主な責務：

```text
startMatch()
submitHand()
completeRound()
advanceMatch()
handleParticipantLeave()
finishNormal()
abortMatch()
```

状態確認から更新完了まで同じGameStateLockを保持する。

### startMatch

RoomService.startMatch()で検証済みのRoom・参加者一覧を受け取る。Controllerから直接呼ばない。

1. 新GameMatchと対戦IDを作成し、roomId・roomNameをコピー。
2. 入室順にMatchParticipantを作成。開始時のユーザーID・名前・手IDをコピーし、score=0・active=true・previousHand=null。
3. 先取勝数・連続禁止設定をコピー。
4. 全参加者のOriginalHandSnapshotを作成し、手名・相性を固定。
5. ラウンド番号1、selections空、startedAt=現在時刻のRoundを作成。対戦状態はSELECTING_HAND。終了関連の初期値は9節に従う。
6. 全コピーの生成完了後にMatchStoreへ登録し、Room.currentMatchIdを設定。
7. 確定した③参加者だけ④へ変更する。

非参加の②・③、②のホストを変更しない。他タブの結果対象も変更しない。本人が④になったことを各タブの状態確認で反映する。

生成失敗では部分登録・一部だけ④の状態を残さない。

### submitHand

次を順に確認する。

- セッションユーザーが④で、現在対戦のactive参加者。
- 送信matchIdがRoom.currentMatchIdおよび当該GameMatch.idと一致。
- 送信roundNumberがcurrentRound.roundNumberと一致。
- state=SELECTING_HAND。
- currentRound.selectionsに本人userIdがない。
- typeと通常手／オリジナル手IDの組合せが正しく、使用可能手である。
- 同一オリジナル手連続禁止違反なし。

対象・状態不一致と二重確定は409 / INVALID_STATE。値不正と連続禁止違反は400 / VALIDATION_ERROR。拒否時は何も更新しない。

API16.0節と同じ順序とし、対象・現在状態・未確定の確認を手の入力値検証より先に行う。現在のmatchId・roundNumberが一致していても、確定済み要求はtype等の値が不正かどうかにかかわらず409 / INVALID_STATEで拒否する。手の値不正を400とするのは、対象・状態・未確定の条件を満たした要求だけとする。

同じ手の再送も別の手への変更も拒否する。古い対戦・ラウンドの要求を現在の入力として扱わない。

手をコピーして登録後、全active参加者が確定した場合だけcompleteRound()を呼ぶ。検証・登録・全員確認・確定まで同じロック内で行う。

### 同一オリジナル手連続禁止

設定ONかつ現在手がORIGINALで、previousHandもORIGINAL、同じoriginalHandIdの場合だけ拒否する。通常手・第1ラウンド・別オリジナル手は制限しない。

### completeRound

state=SELECTING_HAND、activeが2人以上、全activeの選択ありを確認する。不成立・確定済みなら結果を再作成せず更新しない。

1. decidedAtを1回取得し、RoundJudgeServiceへ固定情報を渡す。
2. 返却結果のwonRound=trueの参加者に、ここでだけ1勝加算。
3. 全active参加者のpreviousHandを、今回の本人の手のコピーへ更新。勝者なしでも更新。
4. 変更しないRoundResultをroundHistoryへ1回追加。
5. state=ROUND_RESULT。
6. 先取勝数到達者がいればpendingEndType=NORMAL、pendingWinnerIdsを到達者全員のコピーとする。未決着ならpendingEndType=null・pendingWinnerIds=[]。
7. transitionAt=decidedAt+10秒（勝者あり）または+5秒（勝者なし）。最終ラウンドは必ず10秒。

RoundResult・履歴には累積勝数を持たせない。結果画面のscoresは別の表示用コピーにする。

### advanceMatch

state=ROUND_RESULTかつnow>=transitionAtの場合だけ実行する。

- pendingEndType=NORMAL：finishNormal()。
- 未決着でactiveが2人以上：番号を1増やした空のRoundを作成し、state=SELECTING_HAND・transitionAt=null。score・previousHand・固定情報・過去履歴は保持。
- 未決着でactiveが1人以下：abortMatch()。

既に進んだ対戦・終了済み対戦への再実行は更新しない。

### handleParticipantLeave

当該参加者をactive=falseとする。既にinactiveなら重ねて人数・結果を更新しない。

1. 最終勝者確定済み（ROUND_RESULT・pendingEndType=NORMAL）：確定勝者・結果・勝数・transitionAtを維持。残り0人でも中止しない。
2. 最終勝者未確定かつ残り1人以下：即abortMatch()。確定済み履歴・獲得済み勝数は残す。
3. SELECTING_HANDかつ残り2人以上：退出者の現在selectionsだけ削除し、残存者全員確定ならcompleteRound()。
4. 未決着ROUND_RESULTかつ残り2人以上：確定済みselections・RoundResult・履歴・score・previousHand・transitionAtを変更しない。次ラウンドから対象外とする。
5. MATCH_RESULT：保存済み結果を変更しない。

### finishNormal / abortMatch

finishNormal()は最終ラウンドの期限到達後（Clock等によるnow >= transitionAt）にだけ実行し、pendingEndType=NORMAL・state=ROUND_RESULTを確認する。endType=NORMAL、winnerIds=pendingWinnerIdsのコピーを先に設定する。

abortMatch()は正常勝者未確定の進行中対戦だけに適用し、endType=ABORTED、winnerIds=[]を先に設定する。

その後、同じロック内で以下を1回行う。

1. GameMatchの固定情報と全participantsからMatchResultSnapshotを生成・保存。
2. GameMatch.state=MATCH_RESULTとし、transitionAtを解除。
3. 元roomIdのRoomが存在し、currentMatchIdが当該対戦IDの場合だけ、currentMatchIdを解除しlastCompletedMatchIdを更新。
4. 当該参加者のうち、今も同じルームに所属する④だけ②へ変更。

Roomが削除済みでも結果保存・対戦終了は完了する。roomNameを同名検索して更新先に使用しない。①・他ルーム所属・非参加の②・③を変更しない。

正常勝者確定後の全員退出とルーム削除でも、固定情報だけで結果を保存できる。終了済みへの再実行でSnapshot・新対戦・lastCompletedMatchIdを変更しない。

## 21. MatchResultService

### スナップショット生成

GameMatchのroomId・roomName・固定ルール・全MatchParticipant・確定済み履歴・全OriginalHandSnapshotを使用する。元Room・過去GameUserを参照しない。

active=falseの途中退出者・0勝の参加者もparticipantNamesとfinalScoresへ含める。endType・winnerIdsはMatchServiceが正式確定した値をコピーする。

Map・Listとその要素を変更可能な元オブジェクトと共有せず、保存後に更新しない。同じmatchIdの終了保存は1回だけ。

### 対象の解決と権限

ログイン済み②・③で、指定matchIdの終了スナップショットのroomIdがcurrentRoomIdと一致することを確認する。元参加者だったことは要求しない。

matchId指定ありではその結果だけを解決する。無効な指定を最新へ置き換えない。

指定なしではRoom.lastCompletedMatchIdを一度解決し、対象ID付きURLへ302リダイレクトする。

対戦・観戦から終了時に進むページは、最初から対象matchIdを指定する。結果の対象はページごとに保持し、GameUser・セッションへ共有閲覧先を設定・解除しない。

④は現在対戦へ、①・未ログイン・別ルーム所属はアクセス制御どおりに誘導する。状態・権限確認から表示用コピー生成までGameStateLock内で行う。

勝者名・全参加者名・最終勝数・履歴・相性はMatchResultSnapshotだけから表示用データを生成する。履歴の各RoundResult.entriesはAPIのresultsへ変換し、roundNumberと組み合わせる。現在userState・originalHandは編集用に別途コピーする。

### 保存済み結果の保持

アプリケーション実行中は、保存済みMatchResultSnapshotを新対戦・ルーム退出・ルーム削除・他タブのページ移動で削除しない。ID指定の再読み込みを保証する。再起動時の消失は許容する。

旧ルーム結果を同名の再作成ルームへ公開しない。

## 22. StatusService

GET /api/status用。任意の表示対象matchIdを受け取る。

API26節の全項目・値・null条件を、そのまま応答契約とする。

GameStateLock内でセッションユーザー・所属Room・現在GameMatch・指定対象のGameMatchまたはMatchResultSnapshotを確認し、表示用コピーを作る。lastSeenAtは正常確認時に更新する。

currentMatchId・matchStateは現在ルームの進行中対戦を表し、displayMatchId・displayMatchStateはタブが指定する同一ルームの対象を表す。終了済み指定対象はSnapshotからMATCH_RESULTと判断する。

他ルーム・無効対象のdisplay項目はnullとし、内容を返さない。①はroom・対戦項目をnullにする。未ログインは401のJSON。

room表示用コピーは入室順members・ホスト・ルールだけを含み、手選択・公開前の相性を含めない。状態確認でタブのURLや結果の対象IDを書き換えない。

本人の手確定情報はroom.membersへ入れず、応答直下のselfHandConfirmed・selfSelectedHandとする。表示対象が本人の現在対戦と一致するSELECTING_HANDで、本人が④かつactive参加者の場合だけ、currentRound.selectionsにセッションの本人userIdがあるかを判定する。

- 未確定：selfHandConfirmed=false、selfSelectedHand=null。
- 確定済み：selfHandConfirmed=true、本人のHandSelectionだけからAPI26節のtype・normalHand・originalHandId・handNameをコピーする。手名は通常手の表示名または固定済みOriginalHandSnapshotから解決する。
- 条件外：両項目ともnull。matchId無指定・無効・他ルーム、②・③の観戦、ROUND_RESULT、終了済み結果を含む。

対象ID・ラウンド番号・本人の確定状況・選択手を同じGameStateLock内でコピーし、別タブに古い選択と新しい番号を混在させない。他人の選択・公開前の相性をコピーせず、送信ユーザーIDで本人を変更しない。本人の確定状態をGameUserへ重複保存せず、現在Roundのselectionsを正とする。

## 23. DisconnectMonitor

Spring定期実行を利用し、1秒間隔で確認する。現在時刻は1.3節のClock等から取得する。

②・③・④について、

```text
現在時刻 - lastSeenAt >= 30秒
```

なら期限到達後の次回Monitor実行で切断処理する。期限前には切断しない。

①は対象外。入室成功時にlastSeenAtを入室時刻へ設定する。

監視対象の収集・時刻再確認・退出処理をGameStateLock内で行う。状態確認と競合した場合はロック取得後の最新lastSeenAtで判定し、同じユーザーを二重退出させない。

## 24. MatchTransitionScheduler

500ms間隔で進行中対戦を確認する。現在時刻は1.3節のClock等から取得し、期限前には遷移せず、期限到達後の次回実行で状態を更新する。

```text
state == ROUND_RESULT
&&
現在時刻 >= transitionAt
```

なら、

- 未決着 → 次ラウンド
- `pendingEndType == NORMAL` → 正常終了

へ進める。

対象対戦の再確認からadvanceMatch()の完了までGameStateLock内で行う。Roomが削除されても、最終正常終了待ちのGameMatchをMatchStoreから処理する。古い走査結果で終了や加算を重ねない。

### rooms.js

- オリジナル手作成／編集フォーム開閉。

### room.js

- ルーム名コピー、オリジナル手フォーム開閉。
- 状態JSONのroomから参加者・ホスト・ルール・準備／開始ボタンを更新。

### play.js

- ラウンド履歴開閉、手選択後のボタン制御。
- ページのmatchId・roundNumberを手確定フォームへ設定する。

### round-result.js

- サーバー時刻とtransitionAtから5秒／10秒のカウントを表示。

- 対象が次ラウンドならplay、終了済みなら同じmatchIdのmatch-resultへ移動。

### match-result.js

- 相性表・オリジナル手フォーム開閉。

- URL・ページ制御データのmatchIdを保持し、フォームresultMatchIdへ設定。
- ②・③では他対戦・他タブの操作で結果を切り替えない。

### status-polling.js

currentMatchとdisplayMatchを区別し、②・③の観戦中はdisplay対象の進行・終了へ従う。結果画面の②・③はその対象を維持し、ルーム画面の②・③はルームに留まる。

観戦からの「ルームへ戻る」はそのタブのGET /roomへのページ移動であり、準備状態・他タブの対象を変更しない。

## 29. 排他制御が必要な処理

学習用の本設計では、単一のGameStateLockを全Service・Schedulerで共有し、synchronized（同じ状態への同時更新を防ぐ仕組み）等で保護する。

本文の「共通ロック」「ルーム単位の一連の排他処理」は、この同じGameStateLockで対象処理全体を保護することを指す。

少なくとも以下の確認から更新完了まで、同じロック内で行う。

- セッションユーザーの作成・ログアウトと所属整理。
- 入室の①／未所属確認・検索／作成・8人上限確認・参加登録。
- 最後の退出によるルーム・名前索引の削除、ホスト移譲。
- 準備・取消・ルール変更・オリジナル手保存／削除。
- 開始条件検証から対戦生成・全コピー・③→④。
- 対象matchId／roundNumber確認から手登録・全員確定確認・1回の判定と加算。
- ラウンド遷移・途中退出・切断・終了・結果保存。
- 画面アクセス権限確認・Model生成・状態JSON生成。

Controllerは共通Serviceを経由し、保護されていないMapや変更可能ドメインを直接読み書きしない。外部送信・HTML描画は、ロック内で作った応答用コピーを用いてロック解放後に行う。

同名作成だけ別ロック、同一ユーザーの別ルーム入室だけ保護外、Room削除後の終了だけ保護外、といった分離を行わない。

RoomServiceの検証とMatchServiceの開始、手の未確定確認と登録、ラウンド確定と加算を別の排他区間に分けない。

## 30. 実装順序

本文のパッケージ・API・Serviceの責務は第16段階完了時の最終構成を示す。各段階では、その段階までに登場した型と機能だけに依存してコンパイル・テスト可能な状態を作る。後続段階のクラスやメソッドを先行段階から参照して、コンパイル不能な状態を残さない。

後続機能を含むService・Controller・Form・JavaScriptは、導入済みの範囲から段階的に実装し、後続段階で統合する。途中段階を最終仕様の完成版として扱わず、未導入機能のAPI・画面導線を完成済みとして提供しない。既存のゲーム仕様・検証順序は最終統合時にも変更しない。

### 第0段階：プロジェクト基盤

- Java 21 / Spring Boot 4.1.1 / Gradleを採用する。
- ビルド設定（build.gradle、settings.gradle等）、Gradle Wrapper、Spring Boot起動クラス、基本ディレクトリ構成を作成する。
- Spring Web、Thymeleaf、Validation、Spring Boot Testを使用する。
- DBは使用せず、JPA、H2等のDB関連依存関係を追加しない。
- アプリケーションがコンパイル・起動できる状態までを対象とする。ゲーム機能はまだ対象にしない。
- 本節は今後の実装作業を定義するものであり、設計書修正時にこれらの実装ファイルを作成するものではない。

### 第1段階：Enum

4節のEnumを作成し、コンパイルを確認する。

### 第2段階：基本Domain

- GameUser
- OriginalHand
- Room
- HandSelection

Domainはアプリケーション内のデータと状態を表す型を指す。この段階では対戦用クラスへの参照を導入しない。Room.currentMatchId等のUUIDフィールドは保持できるが、GameMatchの実体には依存しない。

### 第3段階：基本Storeと共有GameStateLock

- UserStore
- RoomStore
- GameStateLock

この段階ではGameMatchやMatchResultSnapshotに依存するMatchStore・MatchResultStoreを作成しない。基本Storeの操作と共有ロックを確認する。

### 第4段階：ログイン・ルームの基本操作

- ログイン・ログアウト。
- ルーム入室・ルーム退出・ホスト移譲、既存のルーム名コピー。
- この段階で必要な共通アクセス制御、Controller・Form・画面。
- 文字列の共通判定と、テストで現在時刻を制御できるClock等の時刻取得基盤。

ログイン・入室・退出・ログアウトの確認は導入済みの①・②を対象とする。準備状態③は第6段階で、対戦状態④の途中退出・ログアウトは第12段階で統合する。RoomService.leaveRoom()等から未導入のMatchServiceを参照しない。状態確認APIと全タブの自動同期は第11段階で統合し、この段階ではサーバー状態と通常の画面要求を確認する。

### 第5段階：オリジナル手の作成・更新・削除

ROOMS・ROOMから利用する機能、各Form、同一画面内のフォーム開閉を完成させる。1.2節のstrip・コードポイント数・保存値・禁止名の基準を適用する。

MATCH_RESULTからの操作・返却先検証・結果ID維持は第14段階で統合する。ここでは未導入の終了済み結果のService・Storeを参照しない。③からの拒否は第6段階、④からの拒否は対戦導入後に確認する。

### 第6段階：準備・ルール

- 準備完了・準備取消。
- ルール変更。
- ③に関係する退出・ログアウト・アクセス制御・オリジナル手操作拒否の統合。

同時準備、重複検証、ルール変更後の③維持を確認する。進行中対戦に関する確認は対戦導入後に実施する。

### 第7段階：対戦関連DomainおよびStore

- GameMatch
- MatchParticipant
- OriginalHandSnapshot
- Round
- RoundResult
- RoundResultEntry
- MatchResultSnapshot
- MatchStore
- MatchResultStore

最終構成で必要な対戦関連DomainとStoreをこの段階でコンパイル可能にする。MatchResultSnapshotの型・コピー構造はここで作成し、終了時の生成・保存・表示機能は第12段階で実装する。

### 第8段階：対戦開始

RoomServiceからMatchServiceへの開始条件検証・委譲、開始時情報の固定、③→④、第1ラウンド生成を実装する。必要な対戦画面と④のアクセス制御を導入する。

全タブの自動同期は第11段階、④の途中退出による継続・中止は第12段階で統合する。この段階では開始処理と生成された対戦状態を確認する。

### 第9段階：手の確定・勝敗判定・ラウンド確定

- 手の確定と勝敗判定。
- 1ラウンド1回だけの確定。
- 勝数加算。
- previousHand更新。
- RoundResultおよび履歴保存。
- transitionAt設定、最終勝者到達時のpendingEndType・pendingWinnerIds設定。

RoundJudgeServiceとMatchService.completeRound()の責務を分離し、確定・加算・履歴保存を重複実行しないことを確認する。同一オリジナル手連続使用制限は第10段階、結果画面は第11段階、終了処理は第12段階、自動遷移は第13段階で統合する。複数ラウンドの判定確認はテスト用データで行い、未導入の自動遷移に依存させない。

### 第10段階：同一オリジナル手連続使用制限

previousHandと開始時ルールに基づく検証・選択可能な手の制御を第9段階へ統合する。通常手・第1ラウンド・別オリジナル手は制限しない。連続ラウンドの検証はテスト用データで実行可能にする。

### 第11段階：ラウンド結果・履歴・状態確認・画面同期

- ラウンド結果画面。
- ラウンド履歴。
- GET /api/statusとStatusService。
- 状態確認、ラウンド結果のカウント、各画面の同期に必要なJavaScript。

2秒間隔の状態確認、導入済み状態の画面遷移、別タブの本人手確定表示、確定前の他人の手・公開前の相性の非公開を確認する。API26節の応答構造を用い、終了済み結果はまだ生成されないため、この段階のテストは導入済みの対象に限定する。終了済み結果・結果画面の同期は第12段階、観戦は第15段階、切断処理は第16段階で統合する。期限到達だけで画面側が次ラウンド・終了を確定しない。

### 第12段階：対戦終了・結果保存・結果画面

- 正常終了・中止と残存④→②。
- MatchResultSnapshotの生成・保存、MatchResultService。
- 対戦結果画面、閲覧条件、対象対戦IDの維持、結果からのルーム戻り。
- ④の手動退出・ログアウトとhandleParticipantLeave()の統合。
- 終了結果の状態確認・画面同期、現在のオリジナル手と過去の相性の分離。
- advanceMatch()から正常終了または次ラウンドへ進む処理。

正常終了はClock等で期限を制御したServiceテストで確認し、期限前にfinishNormal()を実行できないことを確認する。中止は既存の人数不足条件で即時に行う。自動定期実行は第13段階、結果画面からのオリジナル手操作は第14段階、観戦画面は第15段階、通信切断による退出は第16段階で統合する。テスト用の直接呼び出しのために手動次ラウンドAPI・ボタンを追加しない。

### 第13段階：時間経過による自動遷移

MatchTransitionSchedulerを500ms間隔で実行し、第12段階のadvanceMatch()・終了処理を利用する。未決着なら次ラウンド、正常勝者確定済みなら正常終了まで実行可能にする。

期限前の非遷移、期限到達後の次回Scheduler実行による遷移、サーバー変更後の次回状態確認での画面反映を分けて確認する。ルーム削除後の正常終了待ち対戦もMatchStoreから処理する。

### 第14段階：対戦結果画面からのオリジナル手操作

作成・編集・削除を第5段階の機能へ統合する。MATCH_RESULTの返却先検証、対象roomId・resultMatchId、成功後・入力エラー時の同じ結果ID維持、③の編集不可、過去相性表の不変を確認する。

### 第15段階：観戦

同一ルームの非参加②・③の観戦を、画面・アクセス制御・状態確認へ統合する。手選択拒否、確定前の手の非公開、観戦からの戻り、同じ対象IDの結果への遷移、観戦者の状態維持を確認する。

### 第16段階：通信監視・切断処理

DisconnectMonitorを1秒間隔で実行し、入室時刻または最後の正常状態確認＋30秒の期限到達後の次回実行で、既存の退出・対戦継続／中止・正常結果保護へ統合する。共通ロック内で最新lastSeenAtを再確認する。

期限前に切断しないこと、期限到達後のMonitor実行で切断すること、状態確認と競合しても二重退出しないことを確認する。

### 各段階の完了条件と全件確認

各段階では次の順で進める。

```text
実装
↓
コンパイル
↓
その段階までに実行可能な動作確認
↓
その段階までに対応するテスト
↓
次の段階
```

1つのTCが後続機能を含む場合は、導入済み部分を先に確認し、残りは対応段階で統合して確認する。後続段階の機能に関するテストがまだ実行できないことは失敗として扱わない。途中段階の完了は、未導入機能を含む最終仕様の全件合格を意味しない。

第16段階完了後に、05_テスト仕様書のTC-001～TC-130を全件確認する。文字列の共通基準と時間境界は同書2.1・2.2節に従い、実時間の完全一致を合否条件にしない。
