## 2. テスト前提

- 複数ブラウザセッションを用意できる。

### 2.1 文字列の共通判定と境界テスト

ユーザー名・ルーム名・オリジナル手名の前後空白除去、保存、重複判定、文字数判定には、次の共通基準を適用する。

- サーバーでJava `String.strip()`の規則により前後空白を除去する。本書の「前後空白」「空白だけ」の判定も、この規則を基準とする。
- 保存・表示する値と重複判定に使用する値は、除去後の値とする。
- 文字数は除去後のUnicodeコードポイント数（Unicodeの文字を表す符号位置の個数）で数える。Java `String.length()`ではなく、`value.codePointCount(0, value.length())`を使用する。
- 「1～20文字」は、除去後のUnicodeコードポイント数が1～20であることを意味する。未入力または除去後に空になる入力は拒否する。
- JavaScript側のチェックは補助とし、最終判定はサーバーを正とする。

TC-003・007・092・093・119には、この基準の境界確認を含める。ユーザー名・ルーム名・オリジナル手名のそれぞれで、半角スペース・タブ・全角スペースを前後に付けた入力と、それらだけの入力を確認する。除去後の値が保存・表示・重複比較に使われることを確認する。

補助平面の文字（例：単一コードポイントの絵文字）も1コードポイントとして数え、除去後1・20コードポイントは許可、0・21コードポイントは400 / VALIDATION_ERRORとする。文字以外の条件は有効にする。複数コードポイントからなる表示上の1文字は、そのコードポイント数で数える。Java String.length()やHTMLのmaxlengthだけによる誤拒否がないことを確認する。オリジナル手の禁止名判定にもstrip後の値を使用する。

### 2.2 時間依存テストの共通基準

5秒・10秒・30秒はサーバー上の期限として扱い、実時間での画面切替との完全一致を要求しない。

- ラウンド結果の期限は結果確定時刻＋5秒または＋10秒、通信切断の期限は最後の正常状態確認時刻＋30秒とする。入室直後は入室時刻を通信監視の基準とする。
- 期限より前に、時間経過を理由とする状態遷移・切断処理を行ってはならない。
- MatchTransitionScheduler（対戦の自動遷移を確認する定期処理）は500ms間隔、DisconnectMonitor（切断を確認する定期処理）は1秒間隔で確認し、期限到達後の次回実行時に、共通ロック内で最新の状態と時刻を確認して更新する。
- ブラウザーの状態確認は2秒間隔とし、サーバー状態変更後の次回状態確認で表示へ反映されればよい。カウントが0になったことだけで画面側が状態を確定しない。
- 時間依存ロジックはJava `Clock`等（現在時刻を取得する仕組み）を利用し、テストで現在時刻を制御可能にする。期限前の非遷移と期限到達後のScheduler実行による遷移を分けて検証し、実時間の完全一致を合否条件にしない。

人数不足による即時中止や手動退出等、時間経過によらない既存の処理はこの待機期限の対象ではなく、従来どおり実行する。最終勝者確定後は、期限到達後の正常終了処理が完了するまで正常結果の保護と残存参加者の④を維持する。

Clock等で時刻を制御し、期限直前と期限ちょうど（now >= 期限）を分ける。期限前にSchedulerを実行しても更新されないこと、期限到達後の次回実行で更新されること、その後の正常な状態確認でブラウザーへ反映されることを別々に確認する。定期実行設定がMatchTransitionScheduler=500ms、DisconnectMonitor=1秒であることも確認する。

通常起動のClockはTimeConfigurationが提供するUTC基準のClock。Gradleのtestタスクでは`janken.match-transition.enabled=false`・`janken.disconnect-monitor.enabled=false`によりバックグラウンドの定期処理を止め、テストから明示的に実行する。定期処理の登録確認は設定をtrueへ上書きして行い、設定省略時に有効となる条件も確認する。

本書の「5秒後」「10秒後」「30秒切断」「予定時刻」は、サーバー上の期限と期限到達後のScheduler実行を意味する。ネットワーク・処理負荷を含む実時間の完全一致を合否条件にしない。最終勝者確定後は、10秒期限後の実際の正常終了処理まで④と正常結果を維持する。

### 2.3 段階ごとの確認範囲

06_実装設計書の30節に従い、第0～16段階では、その段階までに実装済みの機能だけをコンパイル・動作確認・テストの対象とする。1つのTCが後続機能も要求する場合は実行可能な部分を確認し、未統合部分は後続段階で確認する。未実装の後続機能に関するテストをまだ実行できないことは失敗として扱わない。

Scheduler導入前の時間依存Serviceのテストは、制御可能なClockとServiceの直接呼び出しで確認する。これはテスト内の呼び出しであり、手動の次ラウンドAPIや画面ボタンを追加するものではない。第16段階完了後にTC-001～TC-130の全件確認を行う。

現行の画面・共通処理を確認する追加範囲はTC-131～TC-144とする。これらは確認すべき仕様であり、既存の第16段階完了報告をもって実施済みとは扱わない。自動テスト・ブラウザー確認の実施状況は別途記録する。既存の自動テストと仕様書のTCは件数が一致するとは限らず、テスト成功だけで各TCの全条件を実施済みとしない。

| Mのルームの②、非参加者 | 閲覧可能 |
| Mのルームの③、非参加者 | 閲覧可能、編集導線なし |
| 未ログイン | `/` へ戻す、Mの情報を表示しない |
| 退出済み① | `/rooms` へ戻す、Mの情報を表示しない |
| 他ルーム所属の②・③ | Mの情報を表示しない |
| Mと同じ名前で再作成された別内部IDのルーム所属 | Mの情報を表示しない |
| 現在の新対戦参加者④ | 新対戦の進行状態に合う画面へ遷移 |
| 同一ルームの②・③だが終了済み結果が存在しない | `/room` へ戻す |

他ルーム・再作成前ルームのmatchIdをURLやフォームへ直接指定する統合テスト等でも確認し、ルーム名の一致だけで閲覧を許可しないことを確認する。

### TC-095｜結果スナップショット単独での参加者名・最終勝数再現

前提：

- 開始時の参加者A・B・Cがいる対戦。
- Cが途中退出し、Cの獲得済み勝数がある。
- 正常終了・中止の双方で結果を保存する。

操作：

保存後、結果データ生成のテストで元の `GameMatch` と過去参加者の `GameUser` を参照できない条件を作り、`MatchResultSnapshot` から結果表示用データを生成する。

期待結果：

- A・B・C全員の内部ID・開始時点のユーザー名・最終勝数を再現できる。
- 途中退出したCと0勝の参加者を最終結果から除外しない。
- 勝者名・ラウンド履歴・全オリジナル手相性もスナップショットだけで再現できる。
- 正常終了の勝者と中止時の勝者なしを区別できる。
- その後の現在ユーザー情報・オリジナル手更新で保存結果が変更されない。

前提：M1の対戦・観戦画面がM1のIDを保持している。M1終了後、状態確認と結果表示を一時的に遅らせる。セッション・所属は有効に保つ。

### TC-112｜削除後の返却先と結果ID維持

操作：①のrooms、②のroom、②のM1結果から、それぞれオリジナル手を削除する。

正常時の期待結果：returnPageの対応先へ302で戻る。結果画面ではM1を維持し、M1の相性表を変えない。

拒否条件は次のように分けて確認する。各行では記載した条件以外を有効にし、入力不正の行では操作可能な①・②と正しいreturnPageを使用する。ROOM・MATCH_RESULTの必須IDは各返却先の条件に従う。

## 8. 手確定の検証順序・ログアウトのテスト

### TC-121｜手確定の状態・未確定確認を入力値検証より優先

前提：

- A・B・Cが同じ対戦に参加している。
- B・Cを未確定のままにし、Aが確定してもラウンドが終了しない条件を用意する。
- 送信するmatchId・roundNumberは、値を読み取れる正しい形式とする。

操作：

1. Aが未確定のとき、手の入力値が不正な要求を送信する。
2. Aが有効な手を確定した後、同じ対象に手の入力値が不正な要求を送信する。
3. 古い対戦ID、古いラウンド番号、または手選択中ではない対象に、不正な手の入力値を組み合わせて送信する。

不正な手の入力値には、未定義のtype・normalHand、固定済み手に含まれないoriginalHandId、NORMALなのにoriginalHandIdも指定した組合せ等を使用する。連続使用禁止に違反する再要求も確認する。

期待結果：

| 要求時の条件 | 応答 |
|---|---|
| 現在の対象・手選択中・active参加者・未確定で、手の値だけ不正 | 400 / VALIDATION_ERROR |
| 現在の対象だが本人が確定済みで、手の値も不正 | 409 / INVALID_STATE |
| 対戦・ラウンド・現在状態が不一致で、手の値も不正 | 409 / INVALID_STATE |

- 状態・対象・未確定の確認を、手の入力値検証より優先する。
- 手の入力値が不正でも、確定済み・状態不一致の応答を先に400へ変えない。Controllerから受け取った値を、MatchServiceが対象・状態・未確定の確認後に検証する。
- 拒否要求で提出済み手・勝数・previousHand・履歴・対戦状態を変更しない。
- 未確定時の400では手を登録せず、後から有効な手を確定できる。

### TC-122｜①からの正常ログアウト

前提：

- Aはログイン済みで①、ルーム未所属。
- オリジナル手未作成・作成済みの両方で確認する。

操作：

共通ヘッダーの「ログアウト」からPOST /logoutを実行する。

期待結果：

- 302で `/` へ移動し、ログイン画面を表示する。
- セッションのログイン状態を終了する。①のログイン済み状態として残さない。
- ルーム・対戦・他セッションのユーザー状態を変更しない。
- 元セッションでの保護対象への再アクセスはTC-127に従って拒否する。

### TC-123｜②からのログアウトとルーム退出・ホスト移譲

前提：

- Aはルーム所属の②。
- 非ホスト、他メンバーがいるホスト、ルームの最後の1人の各条件を用意する。
- 進行中対戦の非参加観戦者②としてログアウトする場合も確認する。

操作：

POST /logoutを実行する。

期待結果：

- AをルームのmemberIdsから除外し、セッションのログイン状態を終了する。
- 302で `/` へ移動し、ログイン画面を表示する。
- 非ホストなら既存ホストを変更しない。
- ホストで他メンバーがいる場合は、最も早く入室した残存メンバーへホストを移譲する。
- 最後の1人ならルームとルーム名索引を削除し、その名前で再作成できる。
- 残存ユーザーの②・③・④をログアウトに伴って解除しない。
- Aが現在対戦の非参加者なら、active参加者・選択手・勝数・履歴・対戦状態を変更しない。
- 退出済みのAを後の対戦終了処理で②へ戻さない。

### TC-137｜ルールの要約・開閉・エラー表示と入力保持
